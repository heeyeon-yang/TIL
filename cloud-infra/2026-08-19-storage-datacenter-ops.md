# 2026-08-19 스토리지 ~ 인프라 운영

## 스토리지 연결 방식 (DAS / NAS / SAN)
- DAS: 서버에 직접 연결하는 방식. RAID 구성해서 I/O 성능 올림. 용량/성능/내장애성/확장성 다 고려해야 함
- NAS: 네트워크로 여러 서버가 같이 접근. 데이터 공유하거나 백업/로그 모아둘 때 씀
- SAN: 블록 단위로 데이터 주고받는 전용 네트워크. 속도랑 품질이 제일 좋음 (FC-SAN, IP-SAN)
- 실무에서는 그냥 서버 안에 디스크만 있으면 DAS, 여러 서버가 공유해서 쓰면 NAS/SAN 이렇게 구분하면 됨

## RAID
- 목적은 두 가지: 성능 올리기 + 디스크 하나 죽어도 데이터 안 날아가게 하기
- RAID5: 용량 크게 쓰면서 패리티(복구용 정보) 1개 저장. 대신 좀 느림
- RAID6: 패리티 2개라 디스크 2개까지 동시에 죽어도 버팀. 그만큼 더 느림
- RAID10: 속도는 제일 빠른데 실제 쓸 수 있는 용량이 절반으로 줄어듦
- 핫스페어: 디스크 고장 났을 때 자동으로 대체 투입되는 예비 디스크
- IOPS: 디스크가 초당 처리하는 입출력 횟수. 스트라이핑(여러 디스크에 나눠 쓰기) 개수 늘리면 IOPS도 올라감

## 스토리지 고급 기능
- 씬 프로비저닝: 실제 물리 용량보다 많은 용량을 논리적으로 할당해주는 것 (나중에 실사용량 채워지면 물리 디스크 추가하는 식)
- 자동 계층화: 자주 쓰는 데이터는 빠른 디스크로, 안 쓰는 데이터는 느린 디스크로 자동 이동
- 디둡(중복제거): 이미 저장돼 있는 데이터면 또 복사 안 하고 참조만 함 → 용량 절약
- 스냅샷: 특정 시점 상태를 찍어놓고 나중에 그 시점으로 복원 가능

## 클라우드 스토리지 (AWS 기준)
- EBS: SSD 타입(IOPS 중심, 트랜잭션 많은 DB용) vs HDD 타입(처리량 중심, 로그/스트리밍용)
- EBS 스냅샷은 증분 백업이라 마지막 스냅샷 이후 바뀐 부분만 저장됨 → 용량/비용 아낄 수 있음
- S3는 버킷(폴더 같은 컨테이너) 안에 객체(파일+메타데이터) 저장하는 구조, 객체마다 고유 URL 있음
- S3 스토리지 클래스는 결국 "자주 꺼내 쓰나 vs 오래 묵혀두나"로 고르면 됨
  - 자주 접근 → Standard (비쌈)
  - 가끔 접근 → Standard-IA / One Zone-IA (저장은 싸고 꺼낼 때 비쌈)
  - 접근 패턴을 모르겠다 → Intelligent-Tiering (자동으로 계층 옮겨줌)
  - 거의 안 씀, 장기 보관용 → Glacier / Deep Archive (제일 싸지만 꺼내는 데 몇 시간~반나절 걸림)

## 데이터센터 선정 시 체크할 것
- 입지, 전원 안정성, UPS/발전기 성능, 방재 수준
- 리모트 핸드 서비스 있는지 (직접 못 갈 때 대신 케이블 꽂아주고 재부팅해주는 서비스)

## 장애/병목 대응
- 핫스왑: 서버 끄지 않고 부품(디스크 등) 교체 가능한 기능
- ECC: 메모리 오류 자동으로 감지·보정해줘서 갑자기 시스템 죽는 거 방지
- 병목은 딱 한 군데만 있어도 전체 응답속도가 느려짐 → 병목 의심 지점: 코어/L2 스위치 수용량, 웹서버 메모리, DB의 CPU/메모리/디스크 I/O
- 장애 났을 때 결국 중요한 건 "어디가 병목인지 빨리 찾는 것"
